## ۰) تصمیمِ کلیدیِ کارفرما: سیاستِ سخت‌گیرانه

پیش‌تر گاردِ خروج **اول بی‌صدا ذخیره می‌کرد** و فقط هنگامِ شکست می‌پرسید.
کارفرما صریحاً «سیاستِ سخت‌گیرانه» را انتخاب کرد:

> تا وقتی داده‌ی ذخیره‌نشده هست، **هیچ** خروجی بی‌صدا انجام نمی‌شود.
> همیشه بپرس. سه کنش، همیشه به همان چیدمان.

دلیلِ صنعتی: در نرم‌افزارِ هزینه‌یابی، «ذخیره‌ی بی‌صدا» همان‌قدر خطرناک است که
«دور ریختنِ بی‌صدا» — اپراتور باید بداند **کدام نسخه** روی سرور نشسته است.

### قراردادِ سه کنش (همه‌جا یکسان)

```
┌──────────────────────────────────────────────────────────────┐
│ ترکِ ویرایشگر با داده‌ی ذخیره‌نشده                          ✕ │
│                                                              │
│  ویرایشگر پروژه تغییراتِ ذخیره‌نشده دارد.                    │
│  پیش از رفتن از این صفحه تکلیفشان را روشن کنید.              │
│                                                              │
│ ┌──────────────────┐ ┌──────────────────┐      ┌───────────┐ │
│ │ دور ریختن و رفتن │ │  ذخیره و رفتن    │      │  ماندن    │ │
│ │   (قرمز، خطر)    │ │   (سبز، امن)     │      │ (خنثی)    │ │
│ └──────────────────┘ └──────────────────┘      └───────────┘ │
│   راست = کنشِ اصلیِ RTL       ...            چپِ دور = انصراف │
└──────────────────────────────────────────────────────────────┘
   Esc  =  «ماندن»        (هیچ‌وقت Esc = دور ریختن نیست)
```

قانون‌های ثابت:
1. **کنشِ خطرناک قرمز، کنشِ امن سبز، هر دو `btn-lg` و کنارِ هم** — انتخابِ درست
   باید آسان‌تر از انتخابِ غلط باشد، نه سخت‌تر.
2. **انصراف همیشه دورترین نقطه** (چپِ RTL، کوچک و کم‌رنگ) — هم قانونِ فیتز،
   هم جلوگیری از «کلیکِ اشتباهِ پیاپی».
3. **Esc = ماندن.** اگر کاربر اشتباه کرده، ارزان‌ترین راهِ بازگشت باید کلیدِ
   فرار باشد.
4. **«ذخیره و رفتن» اگر ناموفق باشد، کاربر را نمی‌برد.** پرسش بسته می‌شود،
   خطا توست می‌شود، کاربر در ویرایشگر می‌ماند. رفتنِ بی‌داده هرگز.
5. سه کنش در **هر چهار مسیرِ خروج** یکسان است: ترکِ صفحه (منو / `Alt+1..6` /
   جست‌وجو / hash)، بازکردنِ پروژه‌ی دیگر، «کپی پروژه»، و دکمه‌ی «بستن».

### کدِ مرجع

| مسیر | تابع | فایل |
| --- | --- | --- |
| ترکِ صفحه | `editorExitGuard(ctx)` | `js/ui.js` |
| بستنِ ویرایشگر | `closeProjectEditor()` | `js/ui.js` |
| جابه‌جایی رکورد | `openProjectEditor(id)` | `js/ui.js` |
| لایه‌ی مشترک | `confirmDiscard(msg, {okLabel, okTone, altLabel, altTone, cancelLabel, onAlt})` | `js/ui-modal.js` |
| کنشِ سوم | `#btnConfirmAlt` + `runConfirmAlt()` + `MODALS.confirmAlt` | `js/ui-modal.js` |

`confirmDiscard` یک `Promise<boolean>` برمی‌گرداند: `true` = «دور ریختن» انتخاب شد،
`false` = «ماندن» یا «کنشِ جایگزین انجام شد». پس هیچ callback معلقی نمی‌ماند.

## ۱) نوارِ فرمانِ چسبان (`.editor-bar#editorBar`)

**مسئله (F‑6، C‑5):** دو دکمه‌ی «ذخیره» هم‌وزن در دو جای صفحه بود (سرِ کارت و
نوارِ جمعِ پایین)، و هنگامِ کار با جدولِ بلند هیچ کنشی در دسترس نبود.

**راه‌حل:** یک نوارِ چسبان زیرِ نوارِ بالا، و **یک** دکمه‌ی ذخیره در کلِ صفحه.

```
┌─ topbar (چسبان، z=30، 3.9rem) ────────────────────────────────────────────┐
├─ editor-bar (چسبان، top: var(--topbar-h)، z=24، backdrop-blur) ───────────┤
│ عنوانِ پروژه  [وضعیت]  ● ذخیره‌نشده                                          │
│      ↶ ↷ │ کپی پروژه │ برش‌نامه و خرید │ [صدور فاکتور] [ذخیره Ctrl+S] │ بستن │
└────────────────────────────────────────────────────────────────────────────┘
```

| عنصر | اندازه | چرا |
| --- | --- | --- |
| عنوان + وضعیت + `● ذخیره‌نشده` | متن | کاربرِ وسطِ جدولِ ۶۰ ردیفی باید بداند «روی کدام پروژه» است و «ذخیره کرده یا نه» |
| `↶ ↷` واگرد/بازانجام | `sm icon-only` | کم‌تکرارتر از ذخیره؛ ولی همیشه در دسترس |
| کپی پروژه / برش‌نامه | `ghost sm` / `outline sm` | کنشِ فرعی |
| **صدور فاکتور** | `success btn-lg` | هدفِ بزرگ = قانونِ فیتز |
| **ذخیره** + `<kbd>Ctrl+S</kbd>` | `primary btn-lg` | بزرگ‌ترین هدفِ نوار؛ میان‌برِ کلید **روی خودِ دکمه** نوشته شده (کشف‌پذیری) |
| بستن | `ghost sm`، پس از جداکننده | خروج از کار، خطرناک نیست ولی باید از کنش‌های اصلی **جدا** باشد |

`#edCode` (ورودیِ کدِ پروژه) حذف شد → `#edCodeChip` (نمایشِ فقط‌خواندنی در
کارتِ مشخصات). کدِ پروژه را کاربر وارد نمی‌کند که ورودی بگیرد.

## ۲) نوارِ جمع: باریک + کشوی مالی (F‑2، F‑4)

**مسئله:** نوارِ جمع ۸ ورودی مالی + ۵ عدد + ۴ دکمه را **همیشه باز** نشان می‌داد؛
نیمی از ارتفاعِ صفحه صرفِ چیزهایی می‌شد که در ۹۰٪ مواقع دست‌نخورده می‌مانند.

```
┌─ totalbar (چسبانِ پایین) ───────────────────────────────────────────────────┐
│ ▾ تنظیمات مالی [سود ۲۵٪ • نصب متری • تخفیف ۳٪ • مالیات ۱۰٪]                │
│   هزینه‌ی تمام‌شده  قیمت ناخالص  قیمت هر متر طول  ▮مبلغ قابل پرداخت▯        │
│                                     [ریز قیمت‌ها]  تغییرات ذخیره‌نشده Ctrl+S │
├─ کشو (فقط وقتی باز شود) ────────────────────────────────────────────────────┤
│  روش سود [مارکاپ ▾][۲۵٪]   نصب [متری ▾][350000]   تخفیف [۳٪][مبلغ]          │
│  مالیات (◉) [۱۰٪]   مبلغ ثابت اضافه [...]   پیش‌پرداخت [٪][مبلغ]           │
│  رند کردن [۱ میلیون ▾] [رند کن]                                              │
└────────────────────────────────────────────────────────────────────────────┘
```

- **`#btnTbDrawer`** با `aria-expanded` / `aria-controls`؛ فلشه با `transform: rotate(180deg)`
  جهت را نشان می‌دهد. وضعیتِ کشو در `localStorage["kabir.tbDrawer"]` می‌ماند —
  سلیقه‌ی کاربر است، نه ویژگیِ پروژه.
- **پیش‌فرض: باز.** پنهان‌کردنِ ورودی‌ها نباید به قیمتِ «کشف‌ناپذیری» تمام شود؛
  کاربرِ تازه همه را می‌بیند، کاربرِ قدیمی یک‌بار می‌بندد و همان می‌ماند.
- **`#tbSummary`** خلاصه‌ی زنده‌ی همان ورودی‌هاست («سود ۲۵٪ • تخفیف ۳٪ • مالیات ۱۰٪») —
  پس حتی با کشوی بسته، کاربر **نمی‌تواند** تنظیماتِ فعال را فراموش کند.
  با «بدون تعدیل» وقتی هیچ‌کدام فعال نیست.
- **`#tbSaveHint`** فقط وقتی کثیف است دیده می‌شود: «تغییرات ذخیره‌نشده — `Ctrl+S`».
- دکمه‌های «ذخیره» و «برش‌نامه» از این نوار **حذف** شدند → یک کنش، یک جای ثابت.

## ۳) جدول‌های ویرایشگر: سرِ ستون و ستونِ اولِ چسبان (F‑1، F‑3)

هر ۶ جدول در `.table-wrap.grid-head` نشستند:

```
┌─ .grid-head  (max-height: 56vh، overflow: auto، overscroll-behavior: contain) ┐
│ ┌──────┬──────┬──────┬──────┬─── ...                                            │
│ │ردیف ↕│ نوع  │ طول  │ارتفاع │            ← thead چسبان (top:0، z=3)            │
│ ├──────┼──────┼──────┼──────┼───                                                │
│ │[عنوان]│ ...                                                                  │
│ │ 📋 ⧉ │حذف│  │      │      │            ← ستونِ اول چسبان                       │
│ │  ↑    ↑                                                                        │
│ │  │    └─ جداکننده‌ی `.row-sep` پیش از حذف (F‑3)                                │
│ │  └─ `.row-btns` در `.row-id-cell`                                              │
│ └──────┴──────┴──────┴──────┴───                                                │
└─────────────────────────────────────────────────────────────────────────────────┘
   گوشه‌ی تقاطع (th:first-child) z=6 — روی هر دو می‌نشیند
```

تصمیم‌ها:
1. **کنش‌ها به ستونِ اول آمدند.** پیش‌تر در آخرین سلولِ جدولی تا ۱۲۰۰ پیکسل
   بودند: برای هر حذف باید افقی اسکرول می‌شد (F‑1). حالا با اسکرولِ افقی هم
   همیشه دیده می‌شوند.
2. **حذف از کپی جدا شد.** `.row-sep` یک جداکننده‌ی بصری پیش از دکمه‌ی قرمز است؛
   هدفِ پرتکرار (کپی/الگو) و هدفِ خطرناک (حذف) کنارِ هم بی‌مرز نبودند (F‑3).
3. **هدف‌ها ۲٫۴۵rem (~۳۹px)** و ورودی‌ها `min-height: 2.35rem` — نزدیک به
   آستانه‌ی ۴۰px برای کارِ ۸ ساعته با ماوس (F‑3).
4. **ستونِ اولِ چسبان پس‌زمینه‌ی کدر دارد** (و در `hover` / `focus-within`
   همان رنگِ ردیف) تا ردیف‌های زیرش از آن عبور نکنند.
5. **`overscroll-behavior: contain`**: اسکرولِ جدول به اسکرولِ صفحه سرریز نمی‌کند.

ساختارِ ردیف‌ها عوض شد: عنوان/نام + کنش‌ها همه در **یک** سلولِ اول
(`.row-id-cell`)، و `th` آن «ردیف» (یونیت/درنما/اضافات/خدمات) یا «یونیت»
(درها/کشوها — چون آن‌جا انتخابِ «سعلق به کدام یونیت» نشسته است).

## ۴) حفظِ فوکوس و اسکرول هنگامِ بازسازی (K‑5، K‑6)

**مسئله:** `renderEditorTables()` با `innerHTML` کار می‌کند؛ پس عنصرِ دارای فوکوس
نابود می‌شد و مکان‌نما به `body` می‌پرید. کاربرِ وسطِ تایپ، با یک تغییرِ انتخاب،
به ابتدای جدول پرت می‌شد و باید ردیفش را دوباره پیدا می‌کرد.

**راه‌حل: «هویتِ سلول» به‌جای «اشاره به گره».** DOM عوض می‌شود ولی هویت نه.

```
captureCellFocus()  ── قبل از innerHTML ──►  { scope, k, ui, di, ri, selectionStart, scroll }
                                                       │
renderEditorTables()                                   │
                                                       ▼
restoreCellFocus(keep) ──►  ۱) اسکرولِ ظرف سرِ جایش
                            ۲) اگر _pendingFocus باشد → همان ردیفِ تازه
                            ۳) وگرنه → findCellNode(ident)
                            ۴) focus({preventScroll:true}) + بازگرداندنِ جای مکان‌نما
```

نکته‌ی ظریفِ پیاده‌سازی: در CSS، `[data-di=""]` با «نبودِ صفت» **فرق دارد**.
پس `findCellNode` فقط صفت‌هایی را در گزینش‌گر می‌گذارد که واقعاً مقدار دارند؛
وگرنه سلول پیدا نمی‌شود و فوکوس می‌پرد (این باگ در تست پیدا و رفع شد).

### فوکوسِ «پس از کنش» — `_pendingFocus` / `focusRowAfter(kind, idx, scope, k)`

| کنش | فوکوس می‌رود به |
| --- | --- |
| افزودن ردیف (`＋ یونیت/در/کشو/...`) | ورودیِ **عنوانِ** ردیفِ تازه → کاربر بی‌درنگ تایپ می‌کند، صفر کلیکِ اضافه |
| کپیِ ردیف | ورودیِ عنوانِ **ردیفِ کپی‌شده** |
| حذفِ ردیف | اولین ورودیِ **ردیفِ بعدی** (یا قبلی اگر آخرین بود) |
| «بازگردانی» از توست | همان ردیفِ برگشته |
| واگرد/بازانجام (`Ctrl+Z`) | همان سلولی که رویش کار می‌کردید |

هویتِ ردیف روی `<tr data-row="er:unit:0">` نشسته است. پیشوندِ `er:` عمدی است تا
با `data-row` در مودالِ ساختِ فاکتور قاطی نشود.

> **چرا `busy()` برای این دکمه‌ها استفاده نشد:** `busy(btn)` در بلوکِ `finally`
> همان دکمه را دوباره فعال می‌کند؛ ولی این‌جا خودِ دکمه پس از بازسازی از DOM
> رفته است. مسیرِ درست `_pendingFocus` است، نه نگاه‌داشتنِ اشاره به گره‌ی مرده.

## ۵) ناوبریِ Tab در «ویرایش سریعِ قیمت» (K‑3، K‑4)

سناریوی واقعی: اپراتور صبح ده‌ها نرخ را پشتِ سر هم به‌روز می‌کند.

| کلید | رفتار |
| --- | --- |
| `Tab` | ثبتِ قیمت + بازکردنِ **قیمتِ بعدی** (فوکوس هم منتقل می‌شود) |
| `Shift+Tab` | ثبت + **قیمتِ قبلی** |
| `Enter` | ثبت و ماندن |
| `Escape` | انصرافِ بدونِ ذخیره |
| `Tab` در ابتدا/انتها | توستِ «به اولین/آخرین قیمتِ فهرست رسیدید» |

چون ثبت جدول را از نو رندر می‌کند، مقصد پیش از ثبت در `_qpNavTarget` نگه داشته
می‌شود و `applyQuickPriceNav()` **در پایانِ** `renderMaterials()` اجرا می‌شود —
اگر پیش از آن اجرا شود، همان `innerHTML` ویرایشگرِ تازه‌بازشده را پاک می‌کند
(این هم در تست پیدا و رفع شد). سلولِ مقصد با `dispatchEvent(new MouseEvent("click"))`
باز می‌شود تا رفتارِ Tab و ماوس **دقیقاً یک مسیر** باشد (ثباتِ رویه).

## ۶) بازخوردِ «ذخیره‌نشده» (یک وضعیت، سه نشان)

`paintDirtyState2()` یک تابع است و همه را با هم روشن/خاموش می‌کند:

| نشان | کجا | شکل |
| --- | --- | --- |
| `#btnSaveProject.dirty` | نوارِ فرمان | پس‌زمینه‌ی کهربایی + یک تپشِ یک‌باره (`dirtyPulse`) که با `prefers-reduced-motion` خاموش می‌شود |
| `#ebDirty` + `.editor-bar.is-dirty` | نوارِ فرمان | «● ذخیره‌نشده» |
| `#tbSaveHint` | نوارِ جمع | «تغییرات ذخیره‌نشده — `Ctrl+S`» |

نکته‌ی مهم: پیش‌تر `.dirty::before` فقط یک نقطه‌ی کوچک بود که در عمل دیده
نمی‌شد. حالا **خودِ دکمه** عوض می‌شود — چون دکمه همان جایی است که کاربر برای
رفعِ وضعیت باید نگاه کند.

همچنین فیلدهای سربرگ (`#edTitle` و…) هم به `input` و هم به `change` گوش می‌دهند.
پیش‌تر فقط `change` بود، یعنی تا فوکوس واگذار نمی‌شد برنامه تغییرات را
«ذخیره‌نشده» نمی‌دانست — و اگر کاربر همان‌جا میان‌برِ ناوبری می‌زد، گارد
بی‌خبر می‌ماند. نقضِ قانونِ «هیچ داده‌ای گم نشود».

## ۸) تست‌ها

`tests/ui_modal_guard_check.js` — **۹۹ بررسی**. بخش‌های ۸ تا ۱۱ کامل بازنویسی
شدند چون قرارداد از «ذخیره‌ی بی‌صدا» به «سیاستِ سخت‌گیرانه» تغییر کرد:

- هر سه کنش، **برچسب** و **لحنِ رنگی** و **چیدمانِ DOM** (`btnConfirmOk` پیش از
  `btnConfirmAlt`، انصراف در انتها) سنجیده می‌شود — نه فقط وجودشان.
- «ماندن»/Esc → صفحه عوض نمی‌شود، داده و وضعیتِ کثیف سرِ جایشان.
- «ذخیره و رفتن» → هم رفت، هم داده واقعاً ذخیره شد.
